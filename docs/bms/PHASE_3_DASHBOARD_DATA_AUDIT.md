# Phase 3 — Executive Dashboard Data Audit

**Audit date:** 2026-11-12
**Scope:** Existing BMS Executive Dashboard frontend, current API/controller behavior, authorization, migrations/models/tests, and installed visualization tooling. This audit was completed before Phase 3 implementation.

## Audit evidence and limits

- Frontend: `frontend/src/app/components/bms/dashboard/executive-dashboard.component.{ts,html}`; shared design tokens/primitives in `bms-design-system.scss`, `bms-shared.scss`, and `bms-state.component.*`; `BmsApiService` response/filter mapping.
- API: `GET /api/bms/executive-dashboard` → `ExecutiveDashboardController@index`, protected by `bms.permission:dashboard.view` (`backend/routes/api.php:1462`). Shared option data comes from `GET /api/bms/lookups` / `LookupController@index`. Historical unit KPI data is available from `GET /api/bms/reports/kpis`, protected by `bms.permission:reports.view` (`routes/api.php:1437`).
- Authorization: `BmsAccess::visibleUnitIds()` returns `null` for global-scope roles and an explicit unit-ID list otherwise; selected unit filters call `authorizeUnit`. Opportunity results include records in visible units or owned by the current user. The UI must not broaden these existing rules.
- Schema evidence: repository migrations and Eloquent models, including `2026_11_11_000001_create_bms_phase_one_tables.php`, `2026_11_11_000002_complete_bms_brd_tables.php`, `2026_11_12_000007_add_bms_completion_columns.php`, `000010_add_bms_admin_metadata.php`, and `000011_add_missing_bms_kpi_metadata.php`. **No live database/schema connection was available** (`backend/.env`, `backend/vendor`, and PHP runtime are absent), so deployed schema/data were not independently verified.
- Existing backend coverage includes `P17EmployeeManagementTest::test_P18_dashboard_reports_pending_procurement_upcoming_meetings_and_overdue_tasks`, `test_P20_dashboard_summary_matches_the_widget_data_under_the_same_filters`, recent-activity scope tests, and Phase 1 dashboard card tests. These establish some filter/aggregation behavior but do not run in this checkout without PHP/Composer dependencies.
- `chart.js` 3.7.1 is already declared in `frontend/package.json`, but no BMS or project Angular chart integration was found. Phase 3 can use scoped SVG/CSS visualizations and avoid adding or loading a new chart framework.

## Existing API contract and supported filters

`ExecutiveDashboardController@index` validates `business_unit_id`, `product_id`, `opportunity_id`, and `week_start`.

| Filter | Actual behavior in the current endpoint | Limit / implementation decision |
|---|---|---|
| `business_unit_id` | Authorizes the requested unit; narrows unit/task, opportunity, product, procurement, and meeting queries. | Supported. The current recent-activity feed is scoped to the actor's visible units but does **not** apply the requested unit. A backward-compatible extension of this existing filter is required so the activity feed cannot disagree with a selected unit. |
| `product_id` | Validates against `products`; narrows product rows, narrows opportunities by product, and limits task/unit progress to business units linked to that product. | Supported for those related datasets. It does not filter procurement, meetings, KPI records, or activity; these domains have no product relation in this endpoint. Activity will be omitted while this filter is active rather than implying a product-specific activity feed. |
| `opportunity_id` | Validates the opportunity, authorizes its unit when present, derives its unit/product when those filters are absent, and narrows the opportunities query. | Supported for opportunity/pipeline and inferred unit/product-related data. It does not filter procurement, meetings, KPI records, or generic activity; activity will be omitted while this filter is active. |
| `week_start` | Matches `weekly_plans.week_start` through a `UnitTask.plan` relation, thereby filtering task/unit-progress and task-derived summary counts. | Supported as **Plan week**, not a general date range. It does not filter opportunities, procurement, meetings, products, or KPI history; UI copy must disclose that scope and activity will be omitted while selected. |
| Status | No status filter is validated by the executive endpoint. | Do not expose a status control. Existing output reports statuses/counters but cannot filter every domain by one status. |
| Owner/responsible person | Tasks and opportunities include owner relations, but the executive endpoint has no owner filter parameter. | Do not expose an owner control. |
| Date range / reporting period | No general start/end filter exists on the executive endpoint. The Plan week is exact-match only. | Do not invent a date range or pass unsupported parameters. KPI history uses stored periods; its endpoint does not accept date bounds. |

The pre-implementation component had unit/product/opportunity/`week_start` controls and submitted them to the executive endpoint, but it had no clear/reset action, made an extra `/opportunities` request despite options already being included in scoped lookups, and had no coherent loading/error states or compact viewport layout. The extra request was also unsafe for dashboard-only roles because `/opportunities` requires `opportunities.view`; Phase 3 uses permission-filtered lookup options instead.

## Dashboard implementation decisions from the audit

1. Reuse `GET /executive-dashboard` for operational/pipeline data and its validated filters. Keep its `dashboard.view` permission, unit scoping, and data formulas unchanged.
2. Extend only its recent-activity presentation behavior for the already-supported selected unit, so unit-filtered dashboard data stays coherent. This is a backward-compatible use of the existing `business_unit_id` parameter; no route or permission change is needed. Add focused authorization/filter regression tests. Activity will be hidden for product/opportunity/week selections because the existing audit feed cannot accurately filter those domains.
3. Use `/lookups`' existing permission-filtered options; do not call `/opportunities` separately. Show product, opportunity, and plan-week filters only when the viewer has the corresponding `products.view`, `opportunities.view`, and `plans.view` abilities. Do not expose status, owner, or generic date-range filters.
4. Retrieve KPI history only for viewers with `reports.view`, from the existing protected `GET /reports/kpis` API; the selected business unit is forwarded. Keep series separate by unit and KPI name, do not change the report endpoint or its permission.
5. Present only concise summary/exception cards, business-unit task progress, opportunity stage distribution, unit KPI history when allowed, upcoming meetings, and scoped activity. No duplicate long tables, fabricated forecast/value sums, social metrics, or empty-data zero-to-percent conversions.
6. Use native scoped SVG/CSS charts (installed `chart.js` is present but unused); no new chart library or global shell redesign is needed. Responsive page overflow/height will be measured in real browser QA, with vertical scrolling allowed on tablet/mobile and avoided at the agreed 1440×1000 desktop viewport.

## API contract / backend change rationale

No new endpoint or authorization ability is needed. One optional behavior change is justified: the existing `business_unit_id` filter currently narrows the dashboard's metrics but leaves `recent_activity` at the actor's whole visible-unit scope. Passing that already validated unit ID into the activity scope prevents a selected-unit dashboard from showing unrelated-unit audit events. All other API filter behavior and permission semantics remain unchanged. No migration or database write is required.

## Implementation follow-up — 2026-11-12

The bounded change was implemented: the API now resolves the selected unit for recent activity (including shared product links/product phases), and a focused regression test was added. The frontend uses the existing filter contract and lookup permissions, hides activity when product/opportunity/week filters are active, and gates report history by `reports.view`. Results and remaining verification limits are documented in `PHASE_3_IMPLEMENTATION_REPORT.md` and `PHASE_3_TEST_REPORT.md`. Backend execution, live data reconciliation, browser QA, and screenshots remain outstanding because PHP/database/browser tooling is unavailable in this checkout.
